# Validators

A **checker** decides whether a submission's *output* is correct. A
**validator** decides whether a test's *input* is legal — that `n` really is
in `[1, 10^5]`, that the graph really is connected, that there's exactly one
trailing newline. They're easy to conflate and solve opposite problems.

Without one, a malformed test silently punishes contestants for your
mistake: a solution that correctly assumes `n ≥ 1` gets a WA on the input
where you accidentally wrote `0`.

## The protocol

cxxprobe compiles `validator/validator.cpp` and runs it once per test:

```text
validator <label>          argv[1] is the test's label
  stdin  = the test's .in content
  exit 0        → valid
  exit non-zero → invalid, with stderr as the diagnostic
```

This is exactly [testlib](https://github.com/MikeMirzayanov/testlib)'s
`registerValidation()` / `ensure()` convention, so a testlib validator works
unmodified — cxxprobe doesn't vendor testlib and doesn't need to.

<Callout type="info">
  The validator runs sandboxed under the same machinery as submissions, but
  with deliberately generous limits (512 MiB, 10s CPU, 15s wall) that are
  independent of the problem's own `limits:`. Setter tooling shouldn't
  false-positive a TLE against a contestant-facing time limit.
</Callout>

## Writing one

<Steps>

### Add `validator/validator.cpp`

With testlib:

```cpp
#include "testlib.h"

int main(int argc, char* argv[]) {
    registerValidation(argc, argv);
    int n = inf.readInt(1, 100000, "n");
    inf.readSpace();
    inf.readInt(1, 100000, "m");
    inf.readEoln();
    for (int i = 0; i < n; ++i) {
        inf.readInt(-1000000000, 1000000000);
        inf.readEoln();
    }
    inf.readEof();
    return 0;
}
```

Or without any library at all — the protocol is four lines of contract:

```cpp
#include <cstdio>

int main() {
    int n = 0;
    if (std::scanf("%d", &n) != 1) {
        std::fprintf(stderr, "expected an integer\n");
        return 1;
    }
    if (n < 1 || n > 100000) {
        std::fprintf(stderr, "n = %d is outside [1, 100000]\n", n);
        return 1;
    }
    return 0;
}
```

### Run it

```bash
cxxprobe validate sum-two-numbers
```

```text
Problem: A: Sum Two Numbers

       1: OK
       2: OK
       3: INVALID — n = 0 is outside [1, 100000]

---
INVALID
```

</Steps>

## Options

| Flag | Effect |
|---|---|
| `-C, --dir` | Contest directory (default: auto-detect via `contest.yaml`) |
| `--tests` | Validate an alternate test directory or manifest instead of the problem's own |
| `--json` | Emit the report as JSON |
| `--no-color` | Disable ANSI colour |

Exit codes: `0` valid (or no validator configured — that's a skip, not a
failure), `1` at least one case rejected, `2` a usage or compile error.

`--tests` is useful for checking data you haven't committed yet:

```bash
cxxprobe validate sum-two-numbers --tests /tmp/candidate-tests
```

## With generators

`cxxprobe generate` runs the validator over each freshly generated case
automatically, so a broken generator surfaces immediately rather than at
contest time. See [Generators](/guides/generators).

## Where this sits

There are three separate "is this right?" questions, and cxxprobe keeps them
in three separate commands:

| Command | Question |
|---|---|
| `cxxprobe package validate` | Is the package **structurally** well-formed? |
| `cxxprobe validate` | Does the **test data** satisfy the constraints? |
| `cxxprobe test problem` | Do the **solutions** earn their expected verdicts? |
